# Retrospective — StudyMate AI

When I started this track, my goal was simple on paper and harder in practice: build an AI study assistant that actually felt like a real product, not a demo I'd be embarrassed to link on a resume. I wanted something with a streaming chat interface, tool-backed concept lookup, and a design that didn't look like every other "AI wrapper" project — something with a visual identity of its own.

What I didn't expect was how much of the real work would be in the seams between things, not the AI logic itself. The chat streaming spine came together relatively smoothly once the architecture was clear: a Next.js API route, `streamText` from the AI SDK, and a UI that renders tokens as they arrive. The harder, more instructive part was everything around it — the parts that don't show up in a feature list but are the difference between a toy and something production-shaped.

The single biggest challenge was dependency and build-tooling friction, not application logic. Adding Vercel Analytics broke my install with an `ERESOLVE` peer-dependency conflict. Fixing it locally with `--legacy-peer-deps` wasn't enough, because Vercel runs its own fresh install on deploy and doesn't know about flags I typed manually in my own terminal — that only became obvious after a failed production build, which taught me the real lesson: local success and deployment success are two different guarantees, and a `.npmrc` file is what actually closes that gap. I hit a similar shape of problem again when I added a custom GLSL shader hero using `@react-three/fiber` — a package I'd been assuming was already part of the project (it wasn't), which produced a clean "module not found" error that was a good reminder to verify assumptions about the codebase instead of building on top of them.

The TypeScript "cannot find module" warning on a plain CSS import was its own small lesson in judgment: not every red squiggle is a blocking error, and learning to tell an IDE-level hint apart from something that will actually fail the build saved a lot of time I'd otherwise have spent chasing a non-problem.

Building the shader hero itself was the most rewarding part. Going from "shaders are scary" to actually understanding the `uv` / `u_time` / `u_mouse` mental model well enough to explain every block — the noise-based flow field, the mouse-proximity glow, the vignette keeping text readable — changed how I think about "AI-assisted" work. I didn't just accept generated GLSL; I could walk through why the palette was navy-to-amber (a late-night studying, lamp-light idea tied to the actual product), why the DPR was capped, and why the reduced-motion fallback exists. That's the difference between using AI as a code vending machine and using it as a collaborator I can actually audit.

If I had more time, I'd do three things: add real conversation persistence so refreshing the page doesn't lose chat history; replace the in-memory rate limiter with something that survives a redeploy, since right now a cold start quietly resets everyone's request count; and tie the shader hero's node/glow colors to actual study data, so the hero becomes a live reflection of a user's own progress instead of a purely decorative front door.

The three most transferable things I'm taking from this: first, that production and local environments lie to you differently, and the gap between them is where most "it worked on my machine" bugs live — so I now push and check deploy logs early instead of assuming a working `localhost` means I'm done. Second, that reading an error message fully, rather than pattern-matching to the last error I saw, saves more time than any shortcut — several of my bugs looked alike from the outside but had completely different root causes. Third, that being able to explain a piece of AI-generated code line-by-line is what actually makes it mine — not writing it from scratch, but being able to stand behind every choice in it.
